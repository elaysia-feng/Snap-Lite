# Snap-Lite

Windows 11 x64 原生截图与贴图工具，使用 C++ 和 Win32 实现。支持选区截图、标注、Windows OCR、剪贴板输出和桌面置顶贴图。

## 日常使用

运行 `SnapLite.exe` 后通过托盘或快捷键操作：

| 操作 | 快捷键或方式 |
| --- | --- |
| 开始截图 | `F1` |
| 延时截图（3 / 5 / 10 秒） | 托盘菜单「延时截图」 |
| 全屏截图 | `Ctrl + Shift + F` |
| 将剪贴板图片贴到桌面 | `F3` |
| 完成并复制截图 | `Enter` |
| 取消截图 | `Esc` |
| 撤销 / 重做 | `Ctrl + Z` / `Ctrl + Y` |

选区支持窗口识别、拖动和边缘调整。标注工具包含形状、箭头、画笔、文字、马赛克和橡皮，几何标注可选中后移动或调整大小。

延时截图会在屏幕顶部显示倒计时，点击覆盖层或按 `Esc` 可以取消 —— 用来抓右键菜单、吐司提示这类"刚出现就消失"的界面。

> 倒计时期间覆盖层不抢键盘焦点（`WS_EX_NOACTIVATE`），因此 `Esc` 是靠轮询键盘状态识别的：在**其它程序**里按 `Esc` 也会连带取消这次倒计时。需要稳妥取消时点覆盖层即可。

托盘菜单提供默认保存目录、开机自启和**快捷键说明**（列出全部快捷键，并标出被其他程序占用而注册失败的项）。

## OCR、保存与贴图

OCR 使用 Windows 系统能力，需安装对应语言包。识别在后台线程进行，不会卡住界面；识别结果可选中复制或全部复制，发布版无需 Python 或额外 OCR 模型。

截图可保存为 PNG，并通过剪贴板提供图片和文件表示。能否直接粘贴到终端工具取决于该工具自身是否支持图片输入。

贴图支持置顶、拖动、滚轮缩放和 `Ctrl + 滚轮` 调整透明度；双击或通过右键菜单关闭。托盘菜单可设置默认保存目录和当前用户开机启动。

## 自动更新

应用每天启动时会在后台检查 GitHub 最新正式版。托盘菜单的“自动更新”常驻显示当前版本；点击后会检查最新版本，并在任务栏上方显示检查结果，直到手动关闭。发现新版本后，可从提示框开始下载；更新说明会在安装前显示。安装包通过 SHA-256 校验后才会启动安装程序。安装到需要管理员权限的目录时，Windows 会弹出 UAC 授权。

检查仅请求 GitHub 版本信息，不上传截图或应用设置。没有网络时检查失败不会影响截图功能；也可以随时从托盘菜单手动检查。

## 从源码构建

准备 Windows 11、Visual Studio 2022 的 C++ 桌面开发工具、CMake 3.20+ 和 Python 3。Python 用于构建时生成源码与资源，不是运行时依赖。

推荐使用仓库自带的构建入口，它会自动定位 Visual Studio Build Tools、导入 `vcvars64` 环境并调用 CMake + Ninja：

```powershell
pwsh -NoProfile -File scripts/build_local.ps1
```

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-Tests` | 额外构建原生交互测试并执行 `ctest` |
| `-Clean` | 先清空构建目录再重建（路径必须位于仓库内，否则拒绝删除） |
| `-BuildDir <目录>` | 指定构建目录，默认 `build` |

也可以手动构建：

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

输出为 `build/Release/SnapLite.exe`。如果 CMake 没有找到 Python，在配置命令中通过 `-DPython3_EXECUTABLE=<解释器绝对路径>` 指定。

## 验证与源码入口

- [CMakeLists.txt](CMakeLists.txt)：构建、源码生成与测试选项。
- `src/`：截图、标注、贴图和托盘实现。
- `scripts/`：构建期生成和打包辅助脚本。
- `resources/`：图标与应用资源。
- [docs/improvement-audit-2026-10.md](docs/improvement-audit-2026-10.md)：改进审计报告与修复记录。

原生交互测试通过 `-DSNAPLITE_BUILD_INTERACTION_TESTS=ON` 启用。构建测试目标后执行 `ctest --test-dir build -C Release --output-on-failure`。这类测试会显示真实窗口，需要交互式 Windows 桌面。

`ctest` 现在跑 **5 个用例**：

| 用例 | 内容 |
|---|---|
| `snip_interaction` | **266 项真实 Win32 断言**：选区调整、标注增删改、撤销/重做、**撤销历史的后台压缩与 PNG 解码往返**、**历史被裁剪之后取回的帧必须带着与它配对的那份标注状态**（位图与标注同生共死，不会配对错位）、**产品自己那条“裁剪→编辑→撤销”路径也走一遍同样的配对校验**（上限由产品自己的测试入口压到 2 条，不是压测试自己造的那一份）、**被裁掉的那条历史必须真的裁掉了**（连撤三次，第一个箭头必须还在）、合成图缓存失效路径与 GDI 泄漏检查 |
| `delay_overlay` | **79 项真实 Win32 断言**：延时覆盖层的可见性、**抓屏那一刻它必须已经不在屏幕上**（用覆盖层出现前的基线判定，不受桌面残留像素影响）、`Cancel()` 同步销毁、重复启动不留残影、**等待逻辑本身必须真的在等**（对着一块永远退不干净的区域问产品"退干净了吗"，它必须等满超时才回答）、**产品路径真的调用了等待**（等满上限 / 催过桌面重绘 / 没退回"睡固定时长去赌"）、**基线真的采自屏幕**（事先贴一块同色补丁，产品报出的基线必须对得上；而且必须采自**覆盖层显示之前**的屏幕内容）、**真正交给 Win32 的实参**（交给系统的那块矩形必须非空、必须不擦背景——记录器就放在实参表达式里，换实参或删调用都会当场红）、**请求被拒绝时不能算催过**（让"Windows 拒绝了这次重绘"可以被造出来，计数必须不涨）、**催重绘必须限频**（用户实测"在桌面一测试居然能影响到我桌面二，桌面二在闪"的直接修复点：次数上限用**测试自己量的墙钟** + **测试侧的下限**算，不看产品自报的数；相邻两次的间隔必须真的达到限频值；一次等满上限的等待至少要催两次）、**轮询必须歇息**（歇息时长是量出来的，删掉那行 `Sleep` 就归零；声称的歇息也不能超过等待本身的墙钟；取样次数不能多到变成忙等）、**Start() 拒绝非法参数时不留基线** |
| `build_scripts` | **81 项 Python 断言**：源码级守卫，把结构性不变量（覆盖层状态归属、合成图缓存键覆盖每一个写像素的路径、退出时收掉覆盖层、**无效区外不做全屏合成**、**未定义测试宏时 `#else` 分支按产品代码分析**、**中文 Ninja 构建必须记录 MSVC 头文件依赖**、**等重绘必须拿基线比较且必须有超时上限**、**对桌面窗口的重绘必须限定区域且不擦背景、且计数只在请求真的发出后才涨**、**催重绘必须受一个非恒定的条件约束（`if (true)` 等于不限频）**、**抓不到画面时必须有一条通向 return 的兜底分支**（否则会空转到超时、把界面冻住）、**位图与标注必须存在同一条历史条目里**、**后台线程启动必须异常安全**、**发布链的 tag 闸门必须真的会 throw（而且是直接 throw，不是藏在字符串或嵌套 if 里）**、**失败处理的极性必须对（`$LASTEXITCODE -ne 0` 写成 `-eq 0` 等于把正常发布判成失败）**、**回落开关只能挂在手动触发那条路径上**、DPI 感知的回退与告知……）钉死 |
| `verify_generated_sources` | **46 条产物断言**：生成产物与仓库源文件一致，工具索引使用共享枚举且布局常量来自仓库源码 |
| `update_version` | 纯 C++ 版本号解析与比较，拒绝非数字版本和前导零 |

本地 `scripts/build_local.ps1 -Tests` 与 CI 走的是同一套用例，本地绿灯和 CI 绿灯含义相同。

> 交互测试里的工具栏点击坐标是按 **96 DPI** 写死的。在高缩放显示器上直接跑 `ctest` 可能出现与功能无关的失败；CI 的 `windows-latest` 默认 100% 缩放，不受影响。

> `delay_overlay` 分两段跑：**窗口生命周期**那段（起→取消→窗口没了、重启只留一个）到处都能跑；**像素与等待**那段需要可抓屏的交互式桌面。在没有交互式桌面的会话（例如 CI 的服务 window station）里，像素那段会跳过。
>
> **跳过不等于通过**：只要有任何一组断言被跳过，用例就以退出码 **77** 结束，CMake 侧用 `SKIP_RETURN_CODE 77` 把它认成 "Skipped" 而不是 "Passed"，摘要里也会逐条列出跳过了哪几组。原因是"等待逻辑整个坏掉"在无头环境下本来就验不出来——报成 PASS 等于把没跑的断言说成跑过了。

> 延时覆盖层的测试会在屏幕上短暂出现覆盖层与两块遮挡面板（都在顶部居中与左下角），持续约 7 秒。它们都是 `WS_EX_TOPMOST` 的临时窗口，退出时一定被销毁；测试的重绘请求也只针对那一小块区域，**不会整屏重绘**——桌面窗口横跨所有显示器，整块重绘会让另一块屏跟着闪。

构建期生成管线的回归测试（纯 Python，不需要桌面）：

```powershell
python -m unittest discover -s tests -p "test_*.py"
```

它会完整跑一遍源码生成链，校验生成产物与仓库源文件一致，并把若干结构性不变量（例如延时截图覆盖层的状态归属、合成图缓存键必须覆盖每一个写像素的路径）以源码级守卫的形式钉死。

产物内容校验：

```powershell
python scripts/verify_generated_sources.py build
```

发布版本号解析（纯函数，可单测）：

```powershell
python scripts/resolve_release_version.py --base-version 1.7.4
```
